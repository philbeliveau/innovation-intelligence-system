## Story

**As a** development team maintaining parallel Gradio deployments (local and HF Spaces),
**I want** an automated or semi-automated synchronization workflow that propagates changes from `backend/experimentation/gradio_lab.py` to `backend/experimentation/hf-space-deploy/app.py`,
**so that** feature updates, bug fixes, and improvements are consistently reflected across both environments without manual file copying and divergence risks.

---

## Acceptance Criteria

1. **Divergence Analysis**: Document ALL differences between `gradio_lab.py` (2,022 lines) and `app.py` (2,116 lines), including logging patterns, ID display logic, and line count discrepancies
2. **Sync Mechanism Selection**: Evaluate 4 sync options (Git submodule, manual sync script, GitHub Action, single codebase with environment detection) and recommend ONE approach with technical justification
3. **Automated Sync Implementation**: Implement chosen sync mechanism with validation that changes to main Gradio file trigger HF Spaces updates
4. **Environment Detection**: If single codebase approach chosen, add runtime environment detection (`HF_SPACE_ID`, `SPACE_ID` env vars) to conditionally apply HF Spaces-specific patches
5. **Version Parity Verification**: Create validation script that compares key sections (imports, core functions, pipeline logic) between main and HF Spaces versions and reports mismatches
6. **Dependency Management**: Ensure `hf-space-deploy/requirements.txt` (pinned: gradio==4.44.1) is automatically synced or explicitly documented as requiring manual updates
7. **Supporting Files Sync**: Synchronize copied files (`few_shot_manager.py`, `export/pdf_export.py`) or consolidate to single source with import path resolution
8. **Git History Consolidation**: Address separate `.git/` directory in `hf-space-deploy/` - either remove and use main repo OR document submodule relationship
9. **Documentation**: Update `hf-space-deploy/DEPLOYMENT.md` with sync workflow instructions and frequency recommendations (e.g., "sync before every HF Spaces deployment")
10. **Backward Compatibility**: Existing HF Spaces deployment remains functional during transition (no downtime or breaking changes)
11. **CI/CD Integration**: If GitHub Action chosen, configure workflow to trigger on pushes to `backend/experimentation/gradio_lab.py` with automatic PR creation to HF Spaces repo
12. **Rollback Plan**: Document rollback procedure if sync introduces HF Spaces-specific regressions (e.g., Gradio 5.x compatibility issues from main)

### Sync Mechanism Options (Detailed Analysis)

#### **Option A: Git Submodule**
**Pros:**
- Official Git mechanism for nested repos
- Preserves HF Spaces Git history
- Clean separation of concerns

**Cons:**
- HF Spaces may not support Git submodules (needs verification)
- Complex workflow (`git submodule update --remote` required)
- Sync not automatic (manual submodule update + commit)

**Implementation:**
```bash
# In main repo root
git submodule add https://huggingface.co/spaces/PHILBeli/MBOI-experiment backend/experimentation/hf-space-deploy
git submodule update --remote
git commit -m "chore: update HF Spaces submodule"
```

**Verdict:** ❌ **Not Recommended** - HF Spaces likely doesn't support submodules, too complex

---

#### **Option B: Manual Sync Script**
**Pros:**
- Full control over sync logic
- Can apply HF-specific patches programmatically
- Works with any Git setup

**Cons:**
- Requires manual execution (not automated)
- Potential for human error (forgetting to run script)
- Maintenance burden (script needs updates as files evolve)

**Implementation:**
```bash
#!/bin/bash
# backend/experimentation/sync_to_hf_spaces.sh

set -e

echo "🔄 Syncing gradio_lab.py to HF Spaces..."

# Copy main file
cp backend/experimentation/gradio_lab.py backend/experimentation/hf-space-deploy/app.py

# Apply HF-specific patches
python backend/experimentation/apply_hf_patches.py

# Copy supporting files
cp backend/experimentation/few_shot_manager.py backend/experimentation/hf-space-deploy/
cp backend/experimentation/export/pdf_export.py backend/experimentation/hf-space-deploy/export/

# Commit to HF Spaces repo
cd backend/experimentation/hf-space-deploy
git add .
git commit -m "chore: sync from main gradio_lab.py"
git push origin main

echo "✅ Sync complete! HF Spaces will rebuild in ~3 minutes"
```

**Verdict:** ✅ **Recommended as Baseline** - Simple, predictable, works immediately

---

#### **Option C: GitHub Action (Automated Sync)**
**Pros:**
- Fully automated (no manual intervention)
- Triggers on every push to `gradio_lab.py`
- Can create PRs for review before HF deployment

**Cons:**
- Requires GitHub Actions setup
- Needs HF token for automated push
- Potential for sync failures (CI debugging required)
- May trigger too frequently (every commit syncs)

**Implementation:**
```yaml
# .github/workflows/sync-hf-spaces.yml
name: Sync to HuggingFace Spaces

on:
  push:
    paths:
      - 'backend/experimentation/gradio_lab.py'
      - 'backend/experimentation/few_shot_manager.py'
      - 'backend/experimentation/export/pdf_export.py'
    branches:
      - main

jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout main repo
        uses: actions/checkout@v4

      - name: Run sync script
        run: bash backend/experimentation/sync_to_hf_spaces.sh

      - name: Push to HF Spaces
        env:
          HF_TOKEN: ${{ secrets.HF_TOKEN }}
        run: |
          cd backend/experimentation/hf-space-deploy
          git config user.name "GitHub Action"
          git config user.email "action@github.com"
          git remote set-url origin https://PHILBeli:${HF_TOKEN}@huggingface.co/spaces/PHILBeli/MBOI-experiment
          git push origin main
```

**Verdict:** ✅ **Recommended for Production** - Best long-term solution, but requires setup

---

#### **Option D: Single Codebase with Environment Detection**
**Pros:**
- Single source of truth (no duplication)
- Changes automatically apply to both environments
- No sync mechanism needed

**Cons:**
- Code pollution (HF-specific patches inline)
- Runtime overhead (environment checks on every function call)
- Potential for bugs (wrong environment detection = broken app)

**Implementation:**
```python
# backend/experimentation/gradio_lab.py (consolidated)

import os

def is_hf_spaces() -> bool:
    """Detect HuggingFace Spaces environment"""
    return os.getenv("SPACE_ID") is not None or os.getenv("HF_SPACE_ID") is not None

def log_message(message: str):
    """Environment-aware logging"""
    if is_hf_spaces():
        print(message)  # HF Spaces uses print() for logs
    else:
        import logging
        logger = logging.getLogger(__name__)
        logger.info(message)

def get_experiment_id_display(exp_id: str) -> str:
    """Environment-aware ID formatting"""
    if is_hf_spaces():
        return exp_id[-8:]  # HF shows last 8 chars
    else:
        return exp_id[:8]   # Local shows first 8 chars
```

**Verdict:** ⚠️ **Not Recommended** - Too much conditional logic, harder to maintain

### HF Spaces Deployment Constraints (CRITICAL)

**From `hf-space-deploy/DEPLOYMENT.md`:**

1. **Gradio Version Lock**: MUST use `gradio==4.44.1`
   - Reason: Gradio 5.x has HTTP/2 protocol errors on HF infrastructure (CSS fails to load)
   - Symptom: UI renders black/white, `net::ERR_HTTP2_PROTOCOL_ERROR` in console

2. **Pydantic Version Lock**: MUST use `pydantic>=2.0,<2.9`
   - Reason: Pydantic 2.9+ generates `additionalProperties: true` (boolean) instead of `additionalProperties: {}` (object)
   - Symptom: `TypeError: argument of type 'bool' is not iterable` on startup

3. **No Gradio 5.x Features**: Remove incompatible parameters
   - ❌ `max_height` in Dataframe (added in Gradio 5.x)
   - ❌ `gr.Sidebar()` component (use `gr.Column(scale=1)` instead)

4. **Flat File Structure**: HF Spaces expects all files in root
   - Main uses: `backend/experimentation/gradio_lab.py`
   - HF uses: `app.py` (flat root)
   - Imports must handle both: `from few_shot_manager import ...` (HF) vs `from backend.experimentation.few_shot_manager import ...` (main)

5. **Backend API Differences**:
   - Main uses: `/run/local` endpoint
   - HF uses: `/run` endpoint (Railway production)
   - Parameter name difference: `pdf_text` (main) vs `report_text` (HF)
